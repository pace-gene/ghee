# Bug report — `ghee activity` (found 2026-07-31)

Found while using `ghee` to summarize two weeks of activity for a status
meeting. Cross-checked its output against manual `gh` calls, which is
why the results didn't match on first pass.

## 1. `-u`/`--user` accepts an invalid login with no validation

`_run_activity` (`github_tools/__main__.py:65-79`) resolves the user like:

```python
viewer_login = get_user_login()   # gh api user --jq .login
username = github_user.strip() if github_user and github_user.strip() else viewer_login
```

`get_user_login()` correctly auto-detects the authenticated GitHub login
(e.g. `pace-gene`). But if `-u` is passed, it's used verbatim with no
check that it's a real login. I passed `-u gene.pasquet` (my email, not
my GitHub login) and got silent 404s downstream:

```
gh api users/gene.pasquet/events --paginate ...
Error output: gh: Not Found (HTTP 404)

gh search prs --author gene.pasquet ...
Error output: Invalid search query "author:gene.pasquet ...".
The listed users cannot be searched either because the users do not
exist or you do not have permission to view the users.
```

The tool printed these errors but still produced a full-looking report
(18 Linear issues, `0 commits, 0 PRs`), which reads as "no GitHub
activity" rather than "wrong username, GitHub calls all failed."

**Suggested fix:** validate `-u` against `gh api users/{login}` (or just
`gh api user --jq .login` when unset) before running the rest of the
pipeline, and fail loudly/early if the login doesn't resolve, rather
than proceeding to print a report with zeroed-out GitHub sections.

## 2. PRs from `/users/{user}/events` aren't author-filtered, polluting `activity`'s PR list

`print_activity_summary` (`formatters.py:26`) does:

```python
all_prs = prs + events_summary.get("pull_requests", [])
```

- `prs` comes from `get_pull_requests()` (`github_api.py:136-204`), which
  runs `gh search prs --author {username} --created {from}..{to} ...` —
  correctly author-filtered.
- `events_summary["pull_requests"]` comes from `analyze_events()`
  (`github_api.py:207-240`), built from the `PullRequestEvent` entries
  in `/users/{user}/events` (`github_api.py:229-239`). This endpoint
  returns events for *any* PR the user interacted with — reviewed,
  commented on, merged, labeled, assigned — not just ones they authored.
  There's no author check when appending to `categorized["pull_requests"]`.

Concretely: `ghee activity --from 2026-07-17 --to 2026-07-31 -u pace-gene`
reported 32 PRs, but `gh search prs --author pace-gene --created
2026-07-17..2026-07-31 --json number,repository,title` (the same query
`get_pull_requests()` runs) only returned 30. The two extras
(`pacerevenue/restrictions-recommendation-runner#604` and
`hboetes/mg#37`) were not authored by pace-gene — they came from the
events feed.

Both extras also displayed as "No title" (`formatters.py:87`:
`pr.get("title") or "No title"`), because the events API's
`payload.pull_request.title` field was empty/missing for them — a
separate minor issue, but it's a visible tell that something in the
merged list didn't come from the authoritative `search prs` call.

**Suggested fix:** either drop the events-derived PR list entirely (the
`search prs --author` call already covers "PRs I opened" reliably), or
if the intent is to also show PRs the user reviewed/merged/commented on,
label those separately instead of merging them silently into one PR
count — the current merge makes "N PRs" look like "N PRs I authored"
when it's actually "N PRs I did *something* on".
